A protocol has no workflow states. Order between steps comes from what each action and outcome
needs. A bug fix should show red before the fix and green after it; decision record 0084 settles how
protocols say so, in three steps.

## Now: preconditions

In `software.change/1`, editing the repository is two actions. Writing tests, `tests.write`, has no
precondition. Changing the implementation, `implementation.edit`, needs the case to be a feature or
a refactor, or the claim `regression.reproduced`, which a failing test result establishes. The case
says which kind of change it is in its `change_kind` input when it opens. An agent asking for
`implementation.edit` on a bugfix before red exists gets "blocked", with the claim and the input
that block it as the reasons.

```yaml title="excerpt of protocols/software-change/1.yaml"
case:
  inputs:
    change_kind:
      values: [feature, bugfix, refactor]
claims:
  regression.reproduced:
    true_when:
      evidence: {kind: test_result, result: fail}       # names no subject
actions:
  tests.write:
    effect: write                                       # no precondition
  implementation.edit:
    effect: write
    precondition:
      any:
        - {input: change_kind, in: [feature, refactor]}
        - claim: regression.reproduced                  # a bugfix waits for red
```

Neither action names a capability yet: telling a test edit from an implementation edit needs a path
scope on capabilities, which Canon does not have. The graph is of the shipped protocol; hover
`implementation.edit` to see the precondition that gates it.

## What preconditions cannot say

The precondition admits a history it should not. It asks for a failed test result, but not that the
failure came before the first edit, and not that the failing test is a test of the change. A
failure on an unrelated flake satisfies it.

Canon also binds every evidence record to the current revision of its subject. A failing result
recorded on implementation revision R1 stops counting once an edit produces R2, so a bugfix needs
red recorded again before it edits R2. Keeping red from R1 across the fix needs the evidence-order
or revision-order constructs below.

| Gap | Closed by | Status |
|---|---|---|
| The failing result must come before the fix | an evidence-order predicate: the first `test_result` is `failed`, and it precedes the first implementation diff | decided, not built |
| Red and green must be about the same test, across the fix | revision order: red on revision R1 (test added, fix absent), green on R2 descended from R1, same test id | decided, later |
| A test edit must not touch the implementation | a path scope on capabilities that `tests.write` and `implementation.edit` would require | decided, not built |
| The red result must come from the test runner, not the agent | evidence independence, declared on the evidence kind or the requirement | decided, syntax open |

Until those land, the order is enforced at the moment an action is invoked (the agent cannot edit the
implementation before red exists), and the rest is reviewed.

## Profiles

The red-first rule belongs to bug fixes, not to every change. It is the `bugfix` profile of
`software.change/1`: the value `bugfix` of the case input `change_kind`. A `refactor` omits it, and so
does a `feature` for now. See [Profiles and generated protocols](./profiles-and-generated-protocols.mdx).
