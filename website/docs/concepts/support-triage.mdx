`support.triage/1` is the rules half of a support triage case: one ticket, read at its current
revision, ends `triaged`, `escalated` or `needs_human`. It is the first protocol here outside
software delivery and incident response. Its actions name what is done to a ticket, never the
tracker that holds it; which connection serves `ticket.read` or `ticket.route` is a runtime binding
outside the protocol ([Capabilities and bindings](./capabilities-and-bindings.mdx)). The generated
page, with its graph, is [support.triage/1](../protocols/support-triage/1.mdx).

## What it says

| Step | Action | Effect | Needs |
|---|---|---|---|
| read | `ticket.read` | read | nothing |
| know who asks | `requester.lookup` | read | a current read |
| propose | `ticket.classify` | none | a current read |
| review | `classification.review` | none | a proposal, and authority |
| route | `ticket.route` | write | an approved classification, a known requester, and authority |
| draft a reply | `reply.draft` | write | an approved classification, and authority |
| escalate | `escalation.request` | write | a current read showing the target breached, and authority |

- **Triaged** means category, priority and route are decided on current evidence, for an
  identified requester, with the service-level target not breached.
- **Escalated** means the target is breached and an escalation is requested. The obligation
  `escalate_sla_breach` stays open until a current read shows the target not breached or an
  escalation is requested.
- **Needs human** means the review rejected the classification or the requester could not be
  identified.

The ticket's revision moves when the requester's side of the request changes, not when routing
fields or internal notes change; otherwise the protocol's own writes would make its evidence stale.
When the requester writes again, everything bound to the ticket is `UNKNOWN` until it is read,
classified and reviewed again.

Whether `ticket.route` or `reply.draft` needs a person's approval is policy on the capability in a
composition (decision record 0087), not part of the protocol. Sending a reply to the requester is not
an action of this protocol.

## What Canon cannot say yet

| Gap | What the protocol does instead | Status |
|---|---|---|
| The review must come from someone other than the proposer | nothing; the reviewer holds the `classification.review` capability, which a composition grants. Canon 0.4.0 can demand that a record's producer be independent of the case's work (`independent_on`), but this protocol declares no independence dimension and demands none | planned |
| The review approves *this* classification record, made before it | both are bound to the current ticket revision; the protocol uses none of Canon's evidence-order forms (`first`, `before`), and Canon has no reference from one record to another | planned |
| A category and a priority from the deployment's own lists | a classification is a record; Canon matches one result text and reads no structured value | planned |
| Routing only to queues the case may use | the capability is unscoped; the scope of decision record 0083 is not in Canon | planned |
| An escalation opens an `incident.response` case whose outcome counts here | the escalation is a record; `case.open` and `case_outcome` of decision record 0081 are not in Canon | planned |
| A second classification after a rejection, on the same revision | a rejecting and an approving review of one revision make `classification.reviewed` `UNKNOWN`; the case goes to a person | planned |

The 15-minute expiry of a ticket read is Canon freshness and is shipped. The fixture harness passes
each state's evaluation instant to Canon. Each triage fixture evaluates every state at the
fixture's one instant, at which its read of the ticket's current revision is fresh; the expiry is
tested by evaluating `tri-48213`'s routed state with Canon's evaluator at 15 minutes after the
current read, where triage still holds, and at 16, where the read is expired and `triaged` is no
longer legitimate.
