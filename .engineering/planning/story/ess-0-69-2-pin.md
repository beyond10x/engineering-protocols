## Outcome

The assertion collection's ESS contracts (`ess/` and `ess/providers/`) and CI move from ESS 0.60.0 to ESS 0.69.2 (https://github.com/beyond10x/ess/releases/tag/0.69.2), the newest release on 2026-10-26 (`gh release list -R beyond10x/ess`). Workspace rule (Timo, 2026-10-05): "ALWAYS upgrade to most recent ESS".

## Scope

- `ess/ess-inputs.yaml:2`, `ess/providers/ess-inputs.yaml:2`: `requires: ess 0.69.2`
- `crates/canon-engineering-assertions/generated/`, `crates/assertion-providers/generated/`: regenerated by 0.69.2. A probe on 2026-10-26 (coordinator, scratch copy of `ess/`) found 0.69.2 validates both contracts under `--strict-requires`, compiles them and synthesizes 0 refusals; `generate types` changes the `@generated by ESS` header, `generator_version`, and the generated `Cargo.toml`'s `serde`/`serde_json` requirements from `=` to `^`; `source.schema.json` is byte-identical
- `.github/workflows/check.yml:51-52`: `ESS_VERSION` 0.69.2 and its release checksum `8cc5a3a7ed7c27aacbff131ab1437e18e7d7d1878fee77542b3e0fff7157d414` (the release's `SHA256SUMS`)
- `crates/canon-engineering-assertions/tests/ess_contract.rs`, `crates/assertion-providers/src/lib.rs`, `crates/assertion-providers/README.md`, `AGENTS.md` § ESS: name 0.69.2

## Protocol first

No protocol changes behaviour; exempt. The `ess_contract` tests are the check.

## Acceptance

1. With `ess` 0.69.2 first on PATH, `cargo test -p b10x-canon-engineering-assertions --locked --test ess_contract` passes: both contracts validate under `--strict-requires`, compile, synthesize with 0 refusals, and their generated types match the committed files byte for byte.
2. No file in the repository names ESS 0.60.0 as the current pin (`git grep -n "0\.60\.0"` outside `.engineering/`, `docs/plan/` and `CHANGELOG.md` history is empty).
3. The pull request's `check` run installs ESS 0.69.2 and is green.
